# 工程决策日志

这份文档记录的是项目里**做过的决策、验证方式、以及没带来收益的尝试**——包括负结果。

看架构图只能知道系统长什么样；看这份日志才能判断哪些结论是被数据支撑的、哪些是拍脑袋的。
所有数字都可由 `eval/run_eval.py` 复算，原始数据在 `eval/reports/`。

---

## 一、分阶段验证

每个阶段都配了独立的验证脚本或用例，不是"写完就算做完"。

| 阶段 | 内容 | 验证方式 | 结果 |
|---|---|---|---|
| 一 · 地基 | 配置 / trace / LLM 双后端 / 示例库 / 表画像 / AST 护栏 / 只读执行器 | 护栏专项用例 + 超时中断用例 | 护栏 13/13 通过；超时中断 0.40s 精确生效；写操作被连接层直接拒绝 |
| 二 · 智能层 | Schema Linking（BM25 + 值命中 + 外键扩展 + RRF + LLM 重排）、Prompt 体系、N 候选自一致性投票 | 真实模型验证 | 5 问召回全中；3 问各 3 候选全部执行成功且投票 3/3 一致，含窗口函数 |
| 三 · Agent 编排 | LangGraph StateGraph（条件边 / MemorySaver / interrupt 澄清）、框架无关顺序引擎、流式输出 | FakeLLM 离线用例 + 真实模型冒烟 | 7/7 离线用例通过；真实模型图引擎 2/2 命中 |
| 四 · 评测体系 | 60 题题库（gold SQL 逐条校验）、执行准确率等 9 类指标、消融开关 | 题库构建脚本 + 评测器 | 题库 60/60 校验通过；完整 60 题评测指标见下 |
| 五 · 交付物 | FastAPI（含 SSE 流式）、Streamlit、pytest、Dockerfile / compose | 测试套件 + 目录复跑 | 测试全绿，换目录复跑同样全绿 |

**双引擎的取舍**：LangGraph 图引擎与框架无关的顺序引擎并存。后者存在的意义是——当图引擎的行为需要被排除干扰地验证时，有一条不依赖框架的对照路径；同时也证明编排逻辑本身不是绑死在某个框架里的。

## 二、评测结果与消融

### 2.1 完整 60 题 · 本地 qwen2.5:7b（CPU）· N=3 候选 · 开 LLM 重排 · 开执行自愈

| 指标 | 数值 |
|---|---|
| 执行准确率 EX（严格列序） | 61.2% |
| 执行准确率 EX（列数宽松） | 85.7% |
| SQL 精确匹配 EM | 0.0% |
| 生成 SQL 合法率（过护栏） | 98.3% |
| 歧义澄清率 | 100%（6/6） |
| 危险请求拦截率 | 100%（5/5） |
| 触发执行自愈比例 | 3.3% |
| 延迟 mean / p50 / p95 | 96.9s / 90.0s / 150.7s |
| LLM 调用 / token | 353 次 / 56 万 |
| 数据完整性 | 评测前后所有表行数不变 |

### 2.2 换模型：同一套 Agent、同一个题库

| 指标 | 本地 7B（CPU） | 云端 qwen-max | 变化 |
|---|---|---|---|
| EX（严格列序） | 61.2% | **83.7%** | +22.4pt |
| EX（列数宽松） | 85.7% | **93.9%** | +8.2pt |
| 延迟 p50 | 90.0s | **14.9s** | 快约 6 倍 |
| 窗口函数类 | 14% | **71%** | 最大短板被补上 |
| 由错转对 / 由对转错 | — | **11 题 / 0 题** | 零回退 |

### 2.3 消融：N 候选自一致性投票（同 60 题、同一模型）

| 配置 | EX | 延迟 p50 | token | LLM 调用 |
|---|---|---|---|---|
| N=1（关投票） | 61.2% | 48.7s | 315k | 236 |
| N=3（默认，开投票） | 61.2% | 90.0s | 560k | 353 |

**结论：在这套题库上，投票没有带来准确率提升，却让延迟和 token 接近翻倍。**

原因分析：题目大多是确定性单答案查询，候选之间一致度普遍为 1.0——采样多样性不足时，投票只是在给同一个答案投票。投票的价值要在语义有歧义、采样敏感的问题上才会显现。

处理方式：做成可配置项（`NL2SQL_N_CANDIDATES`）而不是无脑开满，**并保留这条实验记录**。能说清"哪个模块没起作用、为什么"，比硬说"投票提升了准确率"更可信。

### 2.4 A/B：Schema Linking 的向量召回（同义词/口语类 10 题，两边都关 LLM 重排只比召回路）

| 召回路 | 所需表全在 top-6 内 |
|---|---|
| BM25 + 值命中 + 外键扩展 | 8/10 |
| 加上 bge-m3 向量召回 | **10/10** |

漏掉的两题正是字面不重叠的：「售后赔付」（库里叫 refund）和「哪类东西最贵」（口语，库里是类目/商品）。
向量按「模型+文本」哈希落磁盘缓存，59 条文本冷启动 0.3s，之后 0.3ms。

### 2.5 澄清准召的权衡（如实的取舍记录）

从 60 题数据回算出**误澄清率 30.6%**：49 道本可直答的题里有 15 道被反问。

收紧歧义判断后（21 题验证）：误澄清率 **30.6% → 0%**，但该澄清的召回 **100% → 83%**（漏掉的是「我们的大客户都有哪些」这类口径歧义）。

这是准召权衡，如实记录。生产上的做法应该是：对「大客户/活跃/异常」这类口径词建术语白名单强制澄清，并把硬性反问改成"建议式澄清"。

## 三、指标口径定义

NL2SQL 的准确率高度依赖口径，所以四个口径全部保留、全部报出：

| 字段 | 含义 |
|---|---|
| `ex` | 结果集比对，**行序无关、列数与列序都要求一致**，数值带 1e-4 容差 |
| `ex_strict` | 不做数值容差的最严口径 |
| `ex_loose` | 列数宽松：允许多给/少给列，公共列对得上即算对 |
| `ex_relaxed` | 只要求列数一致，允许列序不同 |
| `em` | SQL 字符串精确匹配 |

**为什么 EM 恒为 0 还要保留它**：因为它是"字符串比对不可用"的直接证据。别名不同、多了个 `ROUND`、JOIN 顺序不同，语义完全等价的 SQL 就会被判错。报出 EM=0 是为了说明本项目采用执行结果集比对（Execution Accuracy）的理由。

**为什么要加宽松口径**：复核失败样本时发现，"错"里有一大半是模型善意地多给了一列（问「信用卡支付有多少笔」它顺手带上金额）。这类差异人工判定都算答对，不区分口径会让指标虚低近 25 个百分点。

## 四、踩坑记录

以下是实际浪费过时间的问题，按"再次遇到时能否快速定位"排列。

1. **trace 必须逐题归零**，否则 token 与 LLM 调用次数是跨题累计值，评测指标全废。解法：每题调用前 `Tracer.reset()`。
2. **值命中必须按「表级」做外键扩展**。值 `'华东'` 只出现在 `region.region_name`，而事实表外键指向 `region.region_id`；按列匹配永远扩不到 `orders`，召回会**静默退化**——不报错，只是悄悄变差。
3. **prompt 里的业务口径要限定触发条件**。最初把「活跃客户: is_active=1」写成通用规则后，模型把「一共有多少个客户」算成了活跃客户数。
4. **CTE 名必须从表名集合里排除**，否则 `WITH t AS (...) SELECT * FROM t` 会被表白名单误杀。
5. **sqlglot 对未知函数用 `Anonymous` 表示**，真正的函数名挂在 `.name` 上——只调 `sql_name()` 会漏掉危险函数。
6. **临时脚本别用标准库同名的文件名**。曾因 `_tools/inspect.py` 遮蔽了标准库 `inspect`，导致几乎所有 import 报 `FileNotFoundError`，且报错指向的路径是假象，排查了很久。
7. **embedding 接口也要与对话一样指定计算设备**，否则同样的内核不兼容问题会让 llama-server 直接崩。
8. **本地 GPU 与 Ollama 的 CUDA 内核不匹配**（驱动版本问题）时，会报 `CUDA error: device kernel image is invalid`。代码中默认走 CPU 并做了"GPU 失败自动降级 CPU 并记忆"的处理。

## 五、已知尚未解决的问题

按价值排序，未做就是未做，不做等价交换。

1. **消融实验只做了投票一项**，自愈与重排的消融尚未跑完（`NL2SQL_MAX_REPAIR_ROUNDS=0`、`--no-rerank` 两个开关已就位）。
2. **Top-N 与 HAVING 类题目在本地模型上仍是 0%**，换云端后 Top-N 也只有 50%。这两类需要专项 prompt 或结果后处理。
3. **澄清仍是"硬性反问"**，会打断可直答的问题。理想形态是建议式澄清 + 术语白名单。
4. **存在幻觉未拦截的场景**：问库里没有的「苹果手机」时，模型没返回空集而是给了全库汇总。需要加"查询结果为零时明确说明"的约束。
5. **口径分歧会直接判错**：「每个大类的商品数量」模型按直属商品聚合，标准答案按所有子类汇总。这类需要业务口径表。
